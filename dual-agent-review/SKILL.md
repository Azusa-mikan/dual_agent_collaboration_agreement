# 实现-审查分离（主审查 / 子实现）

把「写代码」和「验收代码」拆给两个不同的 Agent：**主 Agent 只审查，Sub Agent 只实现**。两者不在同一个上下文里，天然不存在「自己写自己审」的偏见。

## 0. 核心原则

- **主 Agent = 审查者。** 唯一能给出「通过 / 不通过」结论的角色。禁止编写或修改源代码。
- **Sub Agent = 实现者。** 只负责实现功能。禁止给出验收结论。
- **上下文隔离即偏见隔离。** Sub Agent 拿到的是一份自包含的任务说明，看不到本次对话历史，因此不会迎合主 Agent 的既有判断；主 Agent 审的是一份外来交付物，不是自己刚写的东西。
- **不引入任何外部状态文件。** 主 Agent 直接同步派发、直接读取 Sub Agent 的汇报、直接判断。通信是一步到位的，无需轮转表、状态机或锁。

## 1. 角色与职责

### 1.1 主 Agent（审查者）

你负责定标准、派活、验收。

- 在与 Sub Agent 相关的整个任务中，保持审查者身份，不承担实现工作。
- 把用户需求翻译成一份**自包含**的任务说明，交给 Sub Agent。说明里要包含：要做什么、改哪些文件、验收标准、约束（用什么技术栈、不能动什么）。
- 派发 Sub Agent 时，**不要把你的判断结论、你的怀疑、你预期的结论写进 prompt**。只给需求和标准，避免污染实现者的产出。
- 收到 Sub Agent 的汇报后，独立验证：
  - 读代码、对比需求。
  - 运行测试（若项目有 `tests` 相关目录）。
  - 可运行编译、类型检查、lint、构建等验证命令。
  - **禁止运行会自动修改文件的命令**（`lint --fix`、`format`、`--write`、`cargo fix` 等）。格式化是 Sub Agent 的职责。
- 给出明确结论：**通过 / 不通过 / 需用户裁决**。禁止含糊带过。
- 不通过时，必须写出可执行的具体问题、与期望的不一致点、阻塞项。
- 可以写改进建议。**建议始终是建议**，不得在后续轮次把已写为「建议」的事项改判为「阻塞」。发现新问题可以新提为阻塞，但不能对同一件事改口。
- 需要返工时，重新派发一个 Sub Agent（或让 Sub Agent 带着明确修复清单继续），把上一轮的阻塞项写成可执行的修复要求。
- 禁止委托「理解」：不要写「根据你的发现去修 bug」「按你的研究去实现」。要写具体文件、行号、改什么。

### 1.2 Sub Agent（实现者）

你只负责实现功能。

- 严格按收到的任务说明实现功能，不扩大范围。
- 完成当前功能后，如果任务说明要求，或项目存在 `tests` 相关目录，就针对该功能补最小测试。
- 如果无法补测试，必须在汇报中说明原因。
- 可以修复实现过程中自己发现的明显问题。
- 可以运行编译、类型检查、lint、构建等**实现性检查**，但**禁止运行任何测试套件**。
- 如果某个命令会同时运行测试，只能运行其中不包含测试的部分；无法拆分时，不要运行，并在汇报中说明。
- 格式化由你负责。项目若有格式化工具，按项目约定运行。
- 禁止以审查者身份审查代码，禁止给出「通过 / 不通过」这类验收结论。
- 汇报必须结构化，至少包含：
  - **改动清单**：每个文件改了什么（文件路径 + 简述）。
  - **测试情况**：补了什么测试、是否运行过、结果如何；没跑或没法跑要说明。
  - **未决事项 / 阻塞点**：没搞定的、拿不准的、需要审查者注意的。
  - **自检声明**：你运行过哪些非测试类检查，结果如何。

Sub Agent 不需要、也不应该被告知本次对话的来龙去脉；它只需要任务说明。

## 2. 标准流程

1. **主 Agent 接收需求。** 明确用户要什么功能、验收标准是什么、有哪些约束。
2. **主 Agent 起草任务说明。** 自包含、可执行、不含结论暗示。若需求本身不清，先向用户确认，不要靠猜。
3. **主 Agent 派发 Sub Agent。** 用可用的子 Agent 机制（如 Agent / Task 工具）派发，把任务说明完整传进去。
4. **Sub Agent 实现并汇报。** 按 1.2 的结构返回结果。
5. **主 Agent 独立验证。** 按 1.1 的方式读代码、跑测试和检查命令。
6. **主 Agent 判定。**
   - **通过**：任务完成，向用户汇报结论。
   - **不通过**：列出具体阻塞项与不一致点，回到第 3 步返工。同一阻塞项最多驳回 2 次；第 3 次必须交用户裁决并停止。
   - **需用户裁决**：需求本身有歧义、或双方僵持、或事务超出本 Skill 授权范围时，停止并交用户。
7. **循环直到通过或需用户裁决。**

主 Agent 不得跳过审查直接宣称完成。Sub Agent 不得自行宣布验收通过。

## 3. 停止与交接话术

停止时话术不固定，但必须让用户一眼看清：**现在卡在哪、需要什么、为什么停。**

- **已通过**：说明任务已通过审查，交付内容是什么。
- **需用户裁决**：说明争议点是什么、双方各自立场、需要用户定什么。
- **需求不清**：说明哪一处不明确，需要用户补充什么，不要自行臆测后开工。
- **Sub Agent 无法交付**：说明 Sub Agent 报的阻塞点，以及你已经尝试过什么。

## 4. 边界

- 主 Agent 禁止直接改代码；发现问题只能描述，交回 Sub Agent 修。
- Sub Agent 禁止下验收结论；它只能说「我做完了、我认为符合 X」，不能说「通过」。
- 两个角色对结论有分歧且无法自行解决时，交用户裁决，不自行认定。
- 需求不清时先问用户，不要替用户决定验收标准。
- 本 Skill 只做本约定授权的事。用户要求做约定之外或明确禁止的事，必须拒绝。

## 5. 为什么不需要外部记录工具

早期版本用两个隔离会话协作，彼此看不见对方，因此需要一份磁盘上的交接日志来做轮转、状态流转和写入互斥。现在改为「主 Agent 同步派发 + 直接读取汇报」后：

- 通信是同一次调用内的请求 / 返回，**不存在跨会话可见性问题**。
- 轮转由流程本身保证（审查者只有一个，就是主 Agent）。
- 状态流转退化为「是否需要返工」这一个判断，由主 Agent 在上下文里直接作出。

因此交接日志、状态机、锁和原子写入全部不再需要。少一层机制，少一处出错点。
